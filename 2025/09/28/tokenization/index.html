tokenization

1. 概述

分词器 (Tokenizer) 是自然语言处理中的基础组件，它的核心作用是在人类可读的文本和机器可处理的数字之间建立桥梁。

具体来说，分词器能够将我们日常使用的文本字符串编码为整数序列，这些整数被称为 token，是模型训练和推理的基本单位。同时，它也能执行相反的过程，将整数序列解码回我们能够理解的原始文本。为了实现这种双向转换，分词器需要维护一个完整的词汇表，这个词汇表定义了所有可能出现的 token 及其对应的整数编号。

1.1 分词方法的评价指标

在深入了解各种分词方法之前，我们需要明确如何衡量一个分词方法的好坏。一个优秀的分词器需要在多个关键指标之间取得平衡，这些指标直接影响着模型的性能、效率和实用性。

词汇表大小 (Vocabulary Size)：这是最直观的指标之一。词汇表过大会导致模型参数量激增，特别是嵌入层的参数会随词汇表大小线性增长。例如，如果词汇表有 10 万个 token，每个 token 用 512 维向量表示，仅嵌入层就需要 5120 万个参数。同时，大词汇表也会增加内存占用和计算开销。

序列长度 (Sequence Length)：对于相同的文本，不同分词方法产生的 token 序列长度差异巨大。序列长度直接影响模型的计算复杂度，特别是对于 Transformer 架构，注意力机制的计算复杂度与序列长度呈平方关系。更长的序列意味着更高的计算成本和内存需求。

压缩率 (Compression Rate)：这个指标衡量分词器将原始文本压缩成 token 序列的效率。压缩率定义为原始字节数与 token 数量的比值。较高的压缩率意味着用更少的 token 表示相同的信息，这不仅提高了计算效率，还能让模型在固定的上下文窗口内处理更多的文本内容。

未登录词处理能力 (OOV Handling)：模型在实际应用中必然会遇到训练时未见过的词汇，如新词、专业术语、人名地名等。一个好的分词器应该能够优雅地处理这些情况，而不是简单地标记为未知符号，避免信息的完全丢失。

此外，还有一些其他考量因素值得关注：分词器应该尽可能保持语义单元的完整性，避免将完整的词过度拆分而破坏语义信息；需要具备一定的多语言适应性，能够处理中文、日文等非空格分隔语言以及混合文本；同时分词器本身的训练和推理效率也不容忽视，过于复杂的算法可能成为系统瓶颈。

在接下来的章节中，我们将通过这些评价维度来分析各种主流分词方法的优缺点，力求理解为什么某些方法在特定场景下更受青睐。

2. 常见分词方法

2.1 字符级分词 (Character-based Tokenization)

字符级分词是最直观的分词方式，它将文本按照单个 Unicode 字符进行切分。Unicode 是一个将字符映射到整数码点 (code point) 的文本编码标准，截至 2024 年 9 月发布的 Unicode 16.0 版本，该标准定义了 154,998 个字符，涵盖 168 种文字系统。每个字符都对应一个唯一的整数 ID，比如字符 “s” 的码点是 115（通常记作 U+0073），而汉字 “牛” 的码点是 29275（通常记作 U+72C2）。在 Python 中，我们可以使用 ord() 函数将字符转换为整数，用 chr() 函数将整数转换回字符：

从实现角度来看，字符级分词几乎不需要任何预处理。你只需要遍历文本中的每个字符，然后查找它对应的 Unicode 码点即可。这种简单性使得它成为很多研究项目的首选，特别是在处理多语言文本或包含大量特殊符号的场景时。

然而，字符级分词也有明显的局限性。首要的问题是词汇表过于庞大（150K+ 的词汇表长度），导致模型的嵌入层参数量激增。另一个问题，大部分 Unicode 字符在实际应用中很少出现，这意味着模型需要为大量低频字符分配参数空间，造成了严重的资源浪费。更糟糕的是序列长度，由于每个字符都是一个 token，原本一个单词可能需要拆分成十几个字符 token，这大大增加了序列的长度。对于基于注意力机制的模型来说，这意味着计算复杂度的平方级增长，严重影响了训练和推理效率。

2.2 字节级分词 (Byte-based Tokenization)

字节级分词采用了一种更加底层的处理方式，它将文本转换为 UTF-8 字节序列，然后将每个字节映射到 0-255 之间的整数。这种方法的最大优势在于词汇表大小固定为 256，相比字符级分词大大减少了词汇表的规模。需要注意的是，UTF-8 编码采用变长编码方式：ASCII 字符如英文字母使用 1 个字节表示，而中文、日文等字符通常需要 3 个字节，一些特殊符号甚至需要 4 个字节。这意味着一个中文字符 “中” 会被拆分成 3 个独立的字节 token（例如：0xE4、0xB8、0xAD），每个字节单独处理。

从实现角度来看，字节级分词非常简单直接，不需要复杂的预处理步骤，这使得它在某些应用场景中颇受欢迎。然而，这种方法也存在明显的问题。首先是压缩率极低，压缩比率等于 1，意味着每个字节对应一个 token，没有实现任何文本压缩。最重要的是，序列长度问题依然严重，甚至可能比字符级分词更糟（存在一个字符多个字节的情况）。由于序列长度过长，这种方法并不适合 Transformer 等基于注意力机制的模型（注意力机制的计算复杂度与序列长度呈平方关系，会严重影响模型的训练和推理效率）

2.3 词级分词 (Word-based Tokenization)

词级分词是最直观的分词方式，它将文本按照自然的词边界进行切分，每个完整的词作为一个独立的 token。这种方法通常使用正则表达式或基于空格的简单规则来识别词边界，比如将 “Hello world” 分解为 [“Hello”, “world”] 两个 token。

从语义角度来看，词级分词具有天然的优势。由于每个 token 都对应一个完整的词，模型能够直接学习到词汇级别的语义表示，这与人类的语言理解方式高度一致。对于许多自然语言处理任务，这种语义完整性能够显著提升模型的理解能力。

然而，词级分词也面临着严峻的挑战。最突出的问题是词汇表规模的爆炸性增长。英语中的词汇数量可能达到数十万甚至上百万，这意味着模型需要为每个词维护一个独立的嵌入向量，导致参数量急剧膨胀。更棘手的是未登录词（Out-of-Vocabulary, OOV）问题：当模型遇到训练时未见过的词汇时，只能将其标记为特殊的 <UNK> 符号，造成信息的彻底丢失。这在处理专业术语、人名、地名或新兴词汇时尤为严重。

2.4 字节对编码 (BPE, Byte Pair Encoding)

BPE 是一种非常流行的子词分词方法，它结合了字节级和词级分词的优点，通过训练自动确定词汇表，常用字符序列用单个 token 表示，罕见序列用多个 token 表示。BPE 的工作原理相对简单而有效：首先从字节级 token 开始构建初始词汇表，然后统计相邻 token 对的出现频率，接着合并最常见的 token 对形成新的 token，并重复这个过程直到达到目标词汇表大小。这种迭代式的合并过程确保了高频的字符序列能够被保留为完整的 token，而低频序列则被拆分为更小的组成部分。正是由于这些优势，BPE 被 GPT-2 等主流语言模型广泛采用，成为了现代自然语言处理的标准分词方法之一。

BPE 被广泛采用的原因在于它巧妙地解决了自然语言处理中的几个关键问题。首先是彻底解决了未登录词 (Out-of-Vocabulary, OOV) 问题。在传统的单词级分词中，模型遇到训练时没见过的词（如专业术语、新词）时，只能将其标记为 <UNK>（未知符号），导致信息丢失。BPE 则将这类罕见词或新词拆解为已知的子词单元，例如将 “unseen” 拆分为 “un” 和 “seen”，从而让模型能够理解和处理之前未见过的词汇。

其次，BPE 在词汇表大小与语义粒度之间取得了巧妙的平衡。单词级分词的词汇表可能异常庞大（英文可达数十万词），导致模型参数爆炸；字符级分词虽然词汇表极小，但序列过长，模型难以学习语义。BPE 通过一个大小可控的词汇表（通常为 3 万至 10 万），既保留了常见词的完整性，又将低频词拆分为有意义的子词单元。

此外，BPE 还具有强大的多语言适应性。它不依赖任何语言的预先定义规则或词典，完全基于数据驱动的学习方式。这使得它能够无缝处理多种语言混合的文本，并对德语、土耳其语等形态变化丰富的语言展现出良好的效果。

3. BPE 算法实现

3.1 BPE 算法的初步实现

BPE 的算法实现遵循如下过程：首先将输入文本转换为 UTF-8 字节序列作为初始 tokens，然后在指定的合并次数内重复执行”统计相邻 token pair 频率→找出最高频的 token pair → 将其合并为新 token → 更新序列”的过程，最终生成一个包含原始 256 个字节 token 加上新合并 token 的词汇表和合并规则表。这种方法巧妙地在词汇表大小可控的前提下，让高频字符序列保持完整性，低频序列被拆分为子词单元，从而解决了传统分词方法中词汇表过大或序列过长的问题，实现了压缩效率与语义保持的平衡。

3.2 BPE 算法实现中的性能问题

上述 naive 的BPE实现虽然在原理上正确，但在处理大规模语料库时存在严重的性能瓶颈。这些问题主要集中在BPE核心更新循环的四个步骤中：

1. 统计相邻 token pair 频率的低效率

当前实现中的 for index1, index2 in zip(indices, indices[1:]): counts[(index1, index2)] += 1 在每次迭代时都要完整遍历整个序列来重新统计所有token对的频率。这种全量统计的方式时间复杂度为O(n)，而整个BPE训练过程需要进行m次合并，总体复杂度达到O(n×m)。实际上，每次合并后只有与被合并token对相关的频率会发生变化，大量的重复计算造成了严重的性能浪费。

2. 找出最高频token pair的搜索效率问题

在编码阶段查找合并规则的优先级时，使用了 list(self.params.merges.keys()).index(pair) 这样的O(n)线性搜索。每次编码都需要进行多次这样的搜索，随着合并规则数量的增加，性能会显著下降。

3. 更新序列时的语义边界问题

直接对整个文本的字节序列进行合并会导致跨词边界的错误合并，产生语义上不合理的token。例如，”dog!”和”dog.”可能会被分配完全不同的token ID，尽管它们在语义上高度相似。

4. 缺乏特殊token处理

当前实现无法处理文档边界、特殊标记等，这在处理多文档语料库时会导致跨文档的错误合并，破坏语义边界。

这些问题的核心在于缺乏预分词(pre-tokenization)步骤和高效的数据结构。解决思路包括：引入预分词来减少统计范围并保持语义边界；使用增量更新只计算受影响的token对频率；预计算合并规则优先级以消除线性搜索；以及在特殊token边界处进行分块处理。具体的优化实现将在3.3节中详细介绍。

3.3 BPE性能优化的解决方案

针对3.2节中提到的四个核心性能问题，我们需要采用系统性的优化策略。这些优化不仅能显著提升BPE训练和推理的效率，还能改善分词的质量和语义一致性。

3.3.1 引入预分词(Pre-tokenization)

问题根源：直接对整个文本的字节序列进行BPE训练会导致计算效率低下和语义边界破坏。

解决方案：在BPE训练之前引入预分词步骤，将文本按照语义边界分割成预token。

优势：

  • 减少了需要统计的token对数量，提高计算效率
  • 保持语义边界完整性，避免跨词的错误合并
  • 支持特殊token的正确处理
3.3.2 增量频率统计优化

问题根源：每次合并后重新统计所有token对频率，造成O(n×m)的时间复杂度。

解决方案：采用增量更新策略，只更新受合并影响的token对频率。

优势：

  • 将频率更新的时间复杂度从O(n)降低到O(k)，其中k是受影响的token对数量
  • 显著减少重复计算，特别是在大规模语料库上效果明显
3.3.3 预计算合并规则优先级

问题根源：编码时使用线性搜索查找合并规则优先级，复杂度为O(n)。

解决方案：在训练完成后预计算所有合并规则的优先级映射。

优势：

  • 将查找合并规则的时间复杂度从O(n)降低到O(1)
  • 编码速度显著提升，特别是在词汇表较大时
3.3.4 特殊token和边界处理

问题根源：缺乏对文档边界和特殊token的处理机制。

解决方案：引入特殊token系统和边界感知的处理机制。

优势：

  • 正确处理文档边界，避免跨文档的错误合并
  • 支持特殊token，增强模型的表达能力
  • 提供更好的语义一致性
3.3.5 综合性能提升

通过上述四个方面的优化，我们可以实现：

  1. 训练效率提升：从O(n×m)降低到接近O(n+m)的时间复杂度
  2. 编码效率提升：从O(n×v)降低到O(n×log v)，其中v是词汇表大小
  3. 内存效率提升：减少重复计算和存储需求
  4. 质量提升：更好的语义边界保持和特殊token支持

这些优化使得BPE分词器能够高效处理大规模语料库，同时保持良好的分词质量，为现代大语言模型提供了坚实的基础。
